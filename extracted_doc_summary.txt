1. Executive summary
IndusInd Bank uses multiple security and infrastructure systems to identify vulnerabilities, manage server inventory, obtain change approvals and execute patching. The operational challenge is to connect these activities into a reliable process in which teams can see the affected server, responsible owner, approved work, execution outcome and closure evidence without maintaining disconnected trackers.
VPM360 will provide a central control point for the lifecycle. It will import Tenable and Squad1 findings, apply agreed normalization rules, correlate server IP addresses with the BMC CMDB, freeze the eligible inventory, and manage change tickets through BMC Helix. Approved patch operations will be coordinated through the tools already used by IndusInd: Red Hat Satellite for Linux, SCCM for Windows, and Automation Controller for approved Database, Middleware and AIX scripts.
Before patching, VPM360 must verify the required gates. After execution, it must collect per-server technical evidence, follow up on security verification and synchronize the permitted ticket and CMDB records. Eight Power BI reports and a detailed governance pack will present the history of each finding, change, execution, exception and closure.
Control remains with IndusInd. Its security teams own assessment outcomes, its change process owns authorization, and its engineering teams own patch content and the automation scripts. VPM360 coordinates the agreed workflow; it does not replace these control functions.
Business outcomes
One traceable finding-to-closure journey across security findings, servers, change approvals and patch jobs.
Less manual reconciliation between Tenable, Squad1, CMDB, Helix and execution tools.
Controlled host selection, maintenance windows, prechecks, execution and postchecks.
Clear accountability for unmatched assets, pending approvals, exceptions, failures and manual rollback.
Consistent management reporting with preserved timestamps, evidence and responsible owners.

5.3 Reusable job lifecycle
Select the patching technology and retrieve the enabled hosts from its configured execution inventory.
Select one or more hosts. Resolve every host to its authoritative CMDB CI and executor identifier; reject ambiguous, inactive or mixed-eligibility selections.
Load Environment, Application Name, IBL SPOC, OS, original Helix change/window and approved patch metadata.
Freeze the target set, patch content and template/script version. Record any permitted edit to effective downtime and require the appropriate approval.
At scheduled time recheck current approval, cancellation, exact host scope, maintenance window, required UAT signoff and patch/content availability.
Execute the configured non-destructive precheck. Only the exact passing hosts proceed.
Submit one approved execution unit per agreed host or group, store the provider operation ID, and poll the status and host outputs.
Validate installed version/update, product and service health, reboot outcome and mandatory script-result markers. Collect raw and normalized evidence.
For failure, block dependent work and send manual rollback handover; for validated execution, record Helix worklog only and wait for the subsequent security/closure decision.
After closure authorization, synchronize the approved CMDB fields and publish the governance records.
5.4 Downtime and scheduling policy
Client shared inputdistinguishes Standard non-production changes and approval-governed production changes. For database and application patching, UAT functional signoff and required application downtime from the product SOP remain applicable even if the generic Standard change does not require formal CAB approval. Production jobs must use the current approved Helix window; an override outside that window is blocked until explicitly re-approved. Mixed environments or non-overlapping approved windows require separate runs unless IndusInd authorizes another rule.
5.5 Manual rollback and exception handling
When a patch fails, VPM360 must preserve the failure evidence, update the Helix worklog with a manual handover to the responsible infrastructure team, and initiate the agreed notification to the asset owner. The technical owner decides and performs repair or rollback under the approved procedure. VPM360 records the result, timestamps, output ID, worklog reference and status. A failed or completed rollback does not automatically close the security finding.
Squad1 exception ID and end date are tracked independently of a exception taken against particular vulnerability. Platform cancelled the tickets and update our power bi report for which vulnerability exception are taken and update exception ID and end date.

Retain both source records and normalized records. Use the source's stable finding identity plus the agreed asset/service scope rather than merging all findings solely by IP or CVE. The bank provides approved API identities and permission scope for each environment. VPM360 will not transmit target-server administrative passwords in browser requests or patch-job parameters. 9.3 Governance lifecycle pack - required controls
The governance pack is a chronological record, not simply a dashboard. Each milestone must record the responsible actor, actual event time, outcome and related evidence/reference. Where several findings belong to one remediation operation, the pack retains each finding and its traceable remediation group and ticket relationship, without collapsing distinct vulnerability identities.
Capture both event time and record-update time where integration latency matters; preserve original source time zone and normalized display time.
Record ticket creation, approval, rejection, cancellation, exception and closure decisions independently of technical execution results.
Record precheck output ID, native patch execution ID, postcheck output ID and manual rollback evidence/reference.
Include Asset Owner Name, the current responsible party, blocked-with owner, blocker reason and the start of the current stage.
Measure elapsed time between significant stages, using the agreed workday/elapsed-hour convention before publishing SLAs.
Retain later reopen and verification history rather than erasing the prior successfully completed actions.
